## The Problem

If you touch Bitcoin, Ethereum, or any ecosystem that inherited Bitcoin’s cryptography choices, you will meet `secp256k1`.

On paper it looks trivial:

- the curve is `y² = x³ + 7`,
- the field is “a big prime modulo”,
- a public key is “just” `Q = k·G`.

But real systems don’t exchange `(x, y)` pairs in Python integers. They exchange **bytes**, and the byte formats have rules:

- compressed vs uncompressed public keys,
- how to “lift” an x-coordinate back to a point,
- what validation must happen before you treat 33 bytes as a public key.

If you don’t understand those rules, you can’t debug interop issues, you can’t review wallet code, and you’ll miss security bugs that look like “just parsing”.

## The Concept

### Domain parameters (what “secp256k1” actually names)

`secp256k1` is a specific set of numbers (SEC 2 calls them “domain parameters”):

- a prime field `F_p` with
  - `p = 2^256 - 2^32 - 977`
- a short-Weierstrass curve
  - `E: y² = x³ + a·x + b (mod p)` with `a = 0`, `b = 7`
- a base point (generator) `G = (Gx, Gy)`
- an order `n` such that `n·G = 𝒪`
- a cofactor `h` (for secp256k1, `h = 1`)

The important consequence of `h = 1` is: there is no “hidden small subgroup” inside the curve group. If a point is on the curve and not infinity, it lives in the same prime-order group generated by `G`.

### Compressed public keys (33 bytes)

An uncompressed public key is:

```text
04 || x (32 bytes) || y (32 bytes)
```

Compressed form drops `y` and keeps only:

```text
02 or 03 || x (32 bytes)
```

The first byte is the parity of `y`:

- `02` means “y is even”
- `03` means “y is odd”

Why is this enough? Because for a given `x`, the curve equation `y² = x³ + 7` has either:

- no solutions (invalid key), or
- two solutions: `y` and `−y (mod p)` (same x, opposite y), which have opposite parity.

So “x + one bit” is enough to recover the full point.

### The one math trick you need: square roots mod p

To recover `y` from `x`, you compute:

```text
rhs = x^3 + 7 (mod p)
y = sqrt(rhs) (mod p)
```

For secp256k1, `p % 4 == 3`, which means a square root (when it exists) can be computed as:

```text
y = rhs^((p+1)/4) (mod p)
```

This is the same “exponentiation trick” you saw in modular arithmetic lessons, just applied to square roots.

### Step 2: Derive a public key from a private scalar

Given a private key scalar `k` (an integer in `[1, n−1]`), the public key is:

```text
Q = k · G
```

In this lesson we use a simple double-and-add scalar multiplication. It’s correct, but the control flow depends on secret bits.

```python
from main import pubkey_from_privkey

Q = pubkey_from_privkey(2)
print(hex(Q.x))
print(hex(Q.y))
```

### Step 3: Serialize and parse public keys (compressed and uncompressed)

This is the interop work you need for real systems: take a point and get bytes, and take bytes and recover the point (or reject).

```python
from main import parse_public_key, serialize_compressed, serialize_uncompressed

pub_bytes = bytes.fromhex(
    "02c6047f9441ed7d6d3045406e95c07cd85c778e4b8cef3ca7abac09b95c709ee5"
)
Q = parse_public_key(pub_bytes)
print(serialize_compressed(Q).hex())
print(serialize_uncompressed(Q).hex()[:12] + "...")
```

### Step 4: Make the warning real (a toy side-channel trace)

Double-and-add does a conditional add only when the current scalar bit is 1. If an attacker can distinguish “double” from “double+add” (timing, power, cache), they learn information about the scalar.

This lesson includes a toy trace:

```python
from main import recover_bits_from_trace, trace_double_and_add

trace = trace_double_and_add(37)
print(trace)
print(recover_bits_from_trace(trace))  # LSB-first bits
```

## Use It

Do not implement secp256k1 yourself for real systems. Use an audited library.

With `cryptography` (OpenSSL backend), deriving a secp256k1 public key looks like:

```python
from cryptography.hazmat.primitives.asymmetric import ec

priv = ec.derive_private_key(2, ec.SECP256K1())
nums = priv.public_key().public_numbers()
print(hex(nums.x))
print(hex(nums.y))
```

For high-performance and constant-time secp256k1 operations in Bitcoin-land, the reference is `libsecp256k1` (bitcoin-core/secp256k1).

## Attack It

### Simple Power Analysis (SPA) intuition

The attack isn’t “break discrete log”; it’s “your implementation leaks”.

Double-and-add does:

- always: a doubling step,
- sometimes: an addition step (only when the bit is 1).

So the pattern of operations (or the timing/power/caches correlated with it) leaks the scalar bits. Real constant-time scalar multiplication routines (ladder-style, or constant-time window methods) are designed to avoid this leak.

Takeaway: correct math is necessary, but not sufficient. Cryptography is engineering under adversarial measurements.

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|----------------------|
| Domain parameters | “the curve” | The full sextuple `(p, a, b, G, n, h)` that defines the group |
| Generator `G` | “a random point” | A fixed point whose multiples generate the group used by the system |
| Order `n` | “size of the curve” | The size of the prime-order subgroup generated by `G` (for secp256k1, the whole group) |
| Compressed key | “just x” | `x` plus 1 bit telling which square root to pick for `y` |
| Lifting | “decode x” | Reconstructing `(x, y)` by solving the curve equation mod `p` |
| Side-channel | “timing issues” | Leakage from control flow/memory/power that reveals secret-dependent behavior |
