## The Problem

If you work with TLS, JWT signing, Apple/Google platform crypto, WebAuthn, OpenSSL, or “enterprise crypto” in general, you will meet **NIST P-256** (also called `secp256r1`).

Most engineers learn P-256 as “just another short-Weierstrass curve”. That’s enough to call a library, but not enough to **review** code safely. P-256 comes with two kinds of footguns:

1) **Trust footguns (the backdoor worry).** The controversy is not “someone demonstrated a backdoor”. The controversy is “the curve generation story is not rigid enough for everyone to trust the constants”.

2) **Engineering footguns (the bugs that actually ship).** Parsing and validating public keys, handling subgroup rules, and avoiding secret-dependent control flow is where real-world vulnerabilities happen.

This lesson makes both concrete: you’ll implement the P-256 parameters + SEC1 point encoding rules, and you’ll learn the exact checks that separate “interoperable and safe” from “works in tests and leaks/accepts garbage”.

## The Concept

### What P-256 actually is

Like secp256k1, P-256 is a *bundle of numbers* (“domain parameters”):

- a prime field `F_p`
- a short-Weierstrass curve `E: y² = x³ + a·x + b (mod p)` with `a = −3 (mod p)`
- a generator point `G`
- an order `n` such that `n·G = 𝒪`
- a cofactor `h` (for P-256, `h = 1`)

The fact that `h = 1` is nice: if a point is on the curve and not infinity, it is already in the prime-order group generated by `G`.

### What people mean by “backdoor” (and what they don’t)

There is no known practical break of P-256 discrete log. The “backdoor” concern is about **parameter generation**:

- If someone gets to *choose* curve constants, could they choose a curve with a hidden weakness known only to them?
- Modern “rigid” curves (like Curve25519) try to reduce this by generating parameters from a clear, deterministic recipe (“nothing up my sleeve numbers”).
- NIST curves historically used a generation process that many engineers find less transparent (especially around how seeds were chosen), so some ecosystems prefer more rigid curves even without a demonstrated attack.

Takeaway: for most systems, the *practical* risks are still implementation bugs and side-channels. But the trust story affects curve selection and long-term confidence.

### The boring-but-important pitfalls

When you accept a peer public key (ECDH, ECDSA verify, etc.), you must:

1. Validate the **encoding** (prefix + length).
2. Validate the **math** (point is on the curve).
3. Enforce **group rules** (subgroup checks / cofactor handling when `h != 1`).
4. Avoid obvious **side-channels** (secret-dependent branches, table lookups).

This lesson focuses on (1) and (2) in code and explains the others clearly.

## Build It

You’ll implement a minimal P-256 toolkit:

- domain parameters + `is_on_curve`,
- scalar multiplication `Q = k·G`,
- SEC1 parsing/serialization for compressed/uncompressed public keys,
- x-lifting via modular square roots (P-256 also has `p % 4 == 3`, so the same exponent trick works as secp256k1).

### Step 1: Confirm the P-256 generator is on the curve

```python
from main import P256, P256_G, is_on_curve

print(is_on_curve(P256, P256_G))
```

### Step 2: Derive a public key `Q = k·G`

```python
from main import pubkey_from_privkey

Q = pubkey_from_privkey(2)
print(hex(Q.x))
print(hex(Q.y))
```

### Step 3: Parse and serialize SEC1 public keys

Compressed keys are `02/03 || x32`. Uncompressed keys are `04 || x32 || y32`.

```python
from main import parse_public_key, serialize_compressed, serialize_uncompressed

Q = parse_public_key(bytes.fromhex("036b17d1f2e12c4247f8bce6e563a440f277037d812deb33a0f4a13945d898c296"))
print(serialize_compressed(Q).hex())
print(serialize_uncompressed(Q).hex()[:12] + "...")
```

### Step 4: Lift x-coordinates by taking square roots mod p

For primes `p ≡ 3 (mod 4)`, a square root (when it exists) can be computed as:

```text
y = rhs^((p+1)/4) (mod p)
```

This is the same trick you used in earlier number theory lessons, just applied to:

```text
rhs = x^3 + a·x + b (mod p)
```

## Use It

Do not implement P-256 yourself for real systems. Use an audited library.

With `cryptography` (OpenSSL backend), P-256 is `SECP256R1`:

```python
from cryptography.hazmat.primitives.asymmetric import ec

priv = ec.derive_private_key(2, ec.SECP256R1())
nums = priv.public_key().public_numbers()
print(hex(nums.x))
print(hex(nums.y))
```

For parsing peer points, prefer library APIs that validate encoding and curve membership (and, when relevant, subgroup rules).

## Attack It

The realistic attacks here are not “solve discrete log”. They are “exploit the places engineers skip checks”.

### Invalid-curve / invalid-point attacks (why `is_on_curve` matters)

If an implementation multiplies a secret scalar by an attacker-provided “point” *without validating it is on the right curve*, the attacker may be able to feed points that live in small groups on related curves over the same field. The victim’s scalar multiplication then leaks the secret scalar modulo small factors.

P-256’s `h = 1` helps, but it does not replace point validation: the attack uses points **not on the curve**.

### Side-channels (why “correct” is not enough)

Our scalar multiplication is double-and-add: the control flow depends on secret bits. This is exactly the kind of pattern that timing/power/cache attacks target. Real libraries use constant-time algorithms.

## Key Terms

| Term | What people say | What it actually means |
|------|----------------|------------------------|
| P-256 / secp256r1 | “the NIST curve” | A specific set of domain parameters `(p, a, b, G, n, h)` |
| Rigid generation | “no backdoor” | Parameters produced by a deterministic recipe with minimal discretion |
| Seed skepticism | “NIST is shady” | Concern about how much freedom existed in choosing the final constants |
| Point validation | “check it’s valid” | Verify encoding and that `(x, y)` satisfies the curve equation mod `p` |
| Invalid-curve attack | “trick ECDH” | Feed points not on the curve to leak secret scalars modulo small factors |
| SEC1 encoding | “compressed keys” | Standard byte formats for points: `02/03||x` and `04||x||y` |
