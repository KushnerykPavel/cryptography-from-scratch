# Groth16 Verifier & Setup Review Checklist

Use this when reviewing a Groth16 verifier (smart contract, on-chain program, backend service) or a PR that touches Groth16 keys/proofs.

## 0) Inputs you must have

- The exact `verifying_key` file (JSON/binary) the verifier will use in production.
- The exact circuit build artifact (R1CS / WASM / constraints count) and the toolchain version (e.g. `circom`, `snarkjs`, `arkworks`, `gnark`).
- At least one known-good proof + public inputs pair generated by the same toolchain and circuit.

If any of these are missing, stop: you cannot review correctness or safety.

## 1) Verifying key sanity checks

- `IC` length matches the number of public inputs **plus 1** (for the constant “1” slot).
- Public input ordering is documented and consistent across:
  - circuit compiler output,
  - prover code,
  - verifier code.
- `alpha`, `beta`, `gamma`, `delta`, and `IC[i]` are not the identity point (unless the scheme/doc explicitly says so).
- `gamma` and `delta` are **independent** parameters (not accidentally identical or derived in a predictable way).
  - If you see `gamma == delta` in G2 for a deployed verifier, treat as a critical red flag.

## 2) Public input handling

- Enforce `len(public_inputs) == len(IC) - 1`.
- Enforce each public input is < field modulus (the scalar field of the curve).
- Ensure any hashing-to-field / packing is deterministic and specified:
  - endianness,
  - byte length,
  - domain separation tags,
  - rejection sampling vs modulo reduction.
- Confirm the constant term is applied exactly once:
  - `vk_x = IC[0] + sum(input[i] * IC[i+1])`.

## 3) Pairing equation correctness

- Verify the equation matches the library’s convention:
  - many implementations check an equivalent “product of pairings equals 1” form using negated points.
- Ensure the correct groups are used:
  - `A, C, IC` are in `G1`,
  - `B, beta, gamma, delta` are in `G2`.
- Confirm the verifier is not mixing affine / Jacobian / precompile encodings incorrectly.

## 4) Trusted setup (ceremony) assumptions

- Groth16 is circuit-specific: changing constraints requires a new setup.
- Confirm the setup was produced by the intended process:
  - single-party setup (high trust),
  - multi-party MPC ceremony (lower trust),
  - reputable “Powers of Tau” + circuit-specific phase, if applicable.
- Confirm the “toxic waste” (trapdoor scalars like τ, α, β, γ, δ or equivalent) is not stored, logged, or recoverable.
- Record the setup transcript/attestation and include it in the repo or release artifacts.

## 5) Testing checklist (non-negotiable)

- Cross-verify:
  - generate proof with toolchain A, verify with toolchain B.
- Include negative tests:
  - mutate one public input → verification must fail,
  - swap public input order → must fail,
  - mutate any proof element (`A`, `B`, or `C`) → must fail.
- If verification runs on-chain, test against the exact on-chain encoding (no “close enough” helpers).

## 6) Common failure modes you can grep for

- Off-by-one in `IC` indexing (`IC[i]` vs `IC[i+1]`).
- Missing field-size checks for public inputs.
- Silent truncation / padding when decoding public inputs.
- Accidentally reusing a verifying key after changing the circuit.
- Using a verifying key from the wrong curve (e.g. BN254 vs BLS12-381).

## 7) Red flags (escalate immediately)

- Any mismatch between circuit artifact and verifying key provenance.
- `gamma_g2 == delta_g2` (or otherwise non-independent) in a deployed verifier.
- “We verified against one proof once” without regression tests.
- “We don’t check public input length / field bounds because it’s expensive.”
