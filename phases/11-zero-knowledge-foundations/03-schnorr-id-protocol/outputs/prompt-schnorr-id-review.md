You are reviewing a design or PR that claims to implement *Schnorr identification* (or “Schnorr proof of knowledge for login”), either interactively or with Fiat–Shamir.

Input you will receive:
- The exact statement being proved (public key / public elements) and the threat model (online login, offline proof, token, etc.).
- The protocol message format (commitment `t`, challenge `c`, response `s`) and the verifier equation.
- How challenges are generated (interactive randomness vs Fiat–Shamir hash).
- Group/curve parameters and serialization rules (including subgroup checks).
- Session context and how it’s bound (user id, server id, domain, timestamp, protocol version, etc.).

Your job:
1) Restate what the protocol *actually* proves (relation `R(statement, witness)`).
2) Identify the highest-risk correctness/security failures first.
3) Propose concrete fixes: validation rules, transcript binding, API changes, tests.

Checklist (answer each with “OK”, “Risk”, or “Fail”):

1) Statement and relation
- Is the statement explicit (e.g., “prove knowledge of `x` such that `y = g^x`”)?
- Is the witness explicit (`x`) and never sent over the wire?
- Does the verifier check exactly `g^s == t · y^c` (or the curve equivalent)?

2) Protocol flow (interactive Schnorr ID)
- Is the challenge `c` generated by the verifier *after* receiving `t`?
- Is `c` unpredictable to the prover before it commits to `t`?
- Is `c` sampled uniformly from a large space (or is repetition used to reduce soundness error)?

3) Replay and session binding (this is where “ZK login” fails in practice)
- Does the verifier enforce freshness (unique session id / nonce / timestamp window) so that old `(t,c,s)` transcripts can’t be replayed?
- Is the statement tied to the correct identity/account (no “log in as someone else” confusion)?
- Is there a clear binding to the server/app context (origin, realm, protocol version)?

4) Fiat–Shamir variant (if used)
- Is `c = H(domain_sep || statement || commitment || session_context || ...) mod q`?
- Does the hash bind *all* public inputs and the commitment `t` (and any message being proven about)?
- Is a domain separation tag/version included and non-empty?

5) Group/curve validation
- Are subgroup membership and invalid-element checks implemented (e.g., `y^q == 1 (mod p)` or curve point validation + subgroup checks)?
- Are identity / small-subgroup / invalid-point edge cases rejected?
- Are scalars reduced mod the correct order and parsed canonically?

6) Nonce (`r`) safety (catastrophic risk)
- Is `r` generated with a cryptographic RNG?
- Is `r` unique per proof/session by construction (no reuse across retries, threads, or contexts)?
- If the API allows caller-supplied `r`, is it forbidden or clearly documented as dangerous?
- Is there a regression test showing nonce reuse leaks `x` (to prove the hazard is understood)?

7) Side channels and production caveats
- Are operations constant-time in the intended environment (or explicitly not claimed to be)?
- Is key material handled carefully (no logs, no accidental serialization of `x` or `r`)?

8) Tests that should exist before merge
- Deterministic vectors: at least one known-good transcript and known-bad transcript.
- Negative tests: wrong statement, wrong challenge, wrong response, invalid group elements.
- Replay test: reusing an old transcript should fail (for interactive login).
- Nonce reuse test: two transcripts with same commitment should allow extracting `x` (demonstrate the hazard).

Output format:
- Summary (2–4 sentences): what is proven, under what assumptions, and how challenges are generated/bound.
- Findings (highest risk first): bullets with concrete failure modes.
- Required changes: specific edits to binding/validation/nonce/session rules.
- Optional improvements: API hardening, domain separation, better test coverage.

Hard fails (if any are true, mark “Fail”):
- Challenge `c` is predictable or not fresh in an interactive login setting (replayable authentication).
- Nonce generation allows reuse of `r` (or commits can be repeated across challenges).
- Fiat–Shamir challenge does not hash the statement and commitment (or lacks domain separation).
- Subgroup membership / point validation is missing where required by the group model.
