## The Problem

Passwords are a terrible interface for secrets: users reuse them, sites store
them badly, phishing steals them, and “login” becomes “send your secret to a
server and hope nothing goes wrong.”

Schnorr identification is a different idea: the prover **never sends the
secret**. Instead, the prover convinces a verifier that they *know* a secret
`x` such that `y = g^x`, by answering a random challenge correctly. If the
verifier is honest, the transcript doesn’t reveal `x`, and if the verifier is
fresh (new challenge each time), transcripts can’t be replayed as logins.

If you don’t understand Schnorr ID, then “zero-knowledge login”, “proof of
knowledge”, and “Fiat–Shamir” remain buzzwords. You won’t be able to review
protocol code for the real failure modes (nonce reuse, missing binding,
subgroup pitfalls, replay).

## The Concept

We work in a prime-order subgroup of `Z_p*`:

- `p` is prime.
- `q` is a prime divisor of `p-1`.
- `g` is an element of order `q`.
- Secret (witness): `x ∈ Z_q`.
- Public statement: `y = g^x (mod p)`.

The identification protocol is a 3-move Σ-protocol run as authentication:

| Move | Sender | Value | Meaning |
|------|--------|-------|---------|
| 1 | Prover | `t = g^r` | “I’m committing to fresh randomness.” |
| 2 | Verifier | `c` | “Answer this random challenge.” |
| 3 | Prover | `s = r + c·x (mod q)` | “Here’s a response consistent with `t` and `x`.” |

Verifier checks a single equation:

`g^s == t · y^c (mod p)`

Why this works (completeness): substitute `s = r + c·x`:

`g^{r + c·x} = g^r · (g^x)^c = t · y^c`.

Why this is safe (intuition): the transcript can be **simulated** without
knowing `x` (against an honest verifier), so it shouldn’t leak `x`. But it is
also **sound**: if someone can answer two different challenges for the same
commitment `t`, they reveal `x`. That’s why **reusing the nonce `r` is
catastrophic**.

## Build It

### Step 1: Parameters, secret, and public statement
```python
@dataclass(frozen=True)
class SchnorrParams:
    """Toy subgroup parameters for Schnorr-style proofs.

    We work in the subgroup of Z_p* generated by g with prime order q.
    """

    p: int
    q: int
    g: int


def schnorr_params_toy() -> SchnorrParams:
    """Small, non-secure parameters for a readable demo."""
    return SchnorrParams(p=23, q=11, g=2)


def schnorr_public_key(params: SchnorrParams, x: int) -> int:
    x = x % params.q
    return mod_pow(params.g, x, params.p)
```
We fix a tiny group so you can compute values by hand while learning the
protocol. The public statement is `y = g^x mod p`.

### Step 2: Interactive Schnorr ID (commit → challenge → response)
```python
def schnorr_id_commit(params: SchnorrParams, r: int) -> int:
    """Commitment t = g^r (mod p)."""
    r = r % params.q
    return mod_pow(params.g, r, params.p)


def schnorr_id_respond(q: int, r: int, c: int, x: int) -> int:
    """Response s = r + c*x (mod q)."""
    return (r + (c % q) * (x % q)) % q


def schnorr_id_verify(params: SchnorrParams, y: int, t: int, c: int, s: int) -> bool:
    """Verifier check for Schnorr ID transcripts."""
    if not (0 <= c < params.q):
        return False
    if not (0 <= s < params.q):
        return False
    if not (0 <= t < params.p):
        return False
    left = mod_pow(params.g, s, params.p)
    right = mod_mul(t, mod_pow(y, c, params.p), params.p)
    return left == right
```
This is the entire identification flow: a commitment, a verifier challenge,
and a response that makes the verification equation true.

### Step 3: HVZK simulation (no secret needed)
```python
def schnorr_id_simulate_hvz(
    params: SchnorrParams, y: int, c: int, s: int
) -> SchnorrIdTranscript:
    """Special HVZK simulator for Schnorr ID.

    Pick (c, s) and compute a commitment t that makes verification pass:
      g^s = t * y^c   =>   t = g^s * (y^c)^(-1)  (mod p)
    """
    c = c % params.q
    s = s % params.q
    y_to_c = mod_pow(y, c, params.p)
    t = mod_mul(mod_pow(params.g, s, params.p), mod_inv(y_to_c, params.p), params.p)
    return SchnorrIdTranscript(t=t, c=c, s=s)
```
The simulator chooses `(c, s)` first, then back-computes a `t` that makes the
verifier accept. If a transcript can be simulated, it has a strong “doesn’t
leak the witness” vibe (against an honest verifier).

### Step 4: Nonce reuse breaks the secret (extract `x`)
```python
def schnorr_extract_secret_from_nonce_reuse(q: int, c1: int, s1: int, c2: int, s2: int) -> int:
    """Recover x from two accepting transcripts with the same commitment and c1 != c2."""
    c1 = c1 % q
    c2 = c2 % q
    s1 = s1 % q
    s2 = s2 % q
    if c1 == c2:
        raise ValueError("need two different challenges to extract")
    num = (s1 - s2) % q
    den = (c1 - c2) % q
    return (num * mod_inv(den, q)) % q
```
If the prover ever reuses `r`, they reuse `t = g^r`. Two different challenges
give you two equations in `x`, and you can solve for `x` in `Z_q`.

### Step 5: Fiat–Shamir preview (binding transcript to context)
```python
def schnorr_fiat_shamir_challenge(
    q: int, *, domain_sep: str, statement_y: int, commitment_t: int
) -> int:
    """Compute a Fiat–Shamir style challenge c = H(context) mod q."""
    if q <= 1:
        raise ValueError("q must be > 1")
    if domain_sep == "":
        raise ValueError("domain_sep must be non-empty")
    msg = f"{domain_sep}|y={statement_y}|t={commitment_t}".encode("utf-8")
    return hash_to_int_sha256(msg, q)
```
Interactive Schnorr ID needs a fresh verifier challenge. Fiat–Shamir replaces
that by hashing the *context* (domain separation + statement + commitment) to
derive `c` deterministically. Binding is the whole point: if you hash the
wrong things, proofs become replayable or transferable.

## Use It

In real systems you rarely ship “Schnorr ID over `Z_p*`” directly. But the
same design pattern appears everywhere:

- **Schnorr signatures:** identification + Fiat–Shamir = signatures (see the next lessons).
- **DLEQ / Chaum–Pedersen proofs:** “I know the discrete log” generalized to equality-of-logs statements.
- **Modern ZK libraries:** transcript frameworks (e.g., Merlin in Rust) provide a standard way to bind context into challenges.

Rule of thumb: if the verifier check is a single algebraic equation and the
protocol is commit → challenge → response, you’re in Schnorr/Σ territory.

## Pitfalls

1. **Nonce reuse (`r`) across sessions:** two transcripts with the same `t` leak `x` immediately.
2. **Replayable challenges:** if the verifier challenge isn’t fresh (or can be predicted), old transcripts can authenticate again.
3. **Not validating subgroup membership:** if `y` (or other points) aren’t in the intended subgroup, verification and security claims can fail.
4. **Tiny challenge space:** soundness error is roughly `1/q`; if `q` is small, cheating is easy unless you repeat rounds.
5. **Unbound transcripts in Fiat–Shamir:** if `c` doesn’t hash the full statement + commitment + domain tag, proofs can be transplanted to other contexts.

## Key Terms

| Term | What people say | What it actually means |
|------|------------------|------------------------|
| Identification protocol | “zero-knowledge login” | An interactive authentication flow where the prover convinces the verifier they know a witness without revealing it. |
| Statement | “public key” | The public value(s) being proved about (here `y = g^x`). |
| Witness | “private key” | The secret value that makes the statement true (here `x`). |
| Nonce | “randomness” | The one-time prover secret `r` that must never repeat; it defines the commitment `t`. |
| Fiat–Shamir | “make it non-interactive” | Derive the challenge by hashing context (statement + commitment + domain separation) instead of sending a random verifier challenge. |
