## The Problem

Sigma (Σ) protocols are the “grammar” of zero-knowledge: once you can recognize
`commit → challenge → response`, you can spot where Fiat–Shamir applies, where
rewinding extractors come from, and where implementation bugs turn a proof into
a key leak.

Without Sigma protocols, you will keep seeing zero-knowledge as magic. You
won’t be able to answer basic engineering questions like:
“What *exactly* is the statement being proved?”, “What does the transcript bind
to?”, “What breaks if I reuse randomness?”, or “Why do we need a transcript
hash in a non-interactive proof?”

In this lesson you build a toy Schnorr Σ-protocol instance and then explicitly
build the two superpowers that make Σ-protocols useful: **simulation** (to show
zero-knowledge against an honest verifier) and **extraction** (to show the
protocol is a proof of knowledge).

## The Concept

A Σ-protocol is a 3-move interactive proof of knowledge for some relation
`R(statement, witness)`. The transcript always has the same shape:

| Move | Name | What it “feels like” |
|------|------|------------------------|
| 1 | commitment `a` | “I’m locking in my randomness.” |
| 2 | challenge `c` | “I’m forcing you to answer *this* question.” |
| 3 | response `s` | “Here’s an answer consistent with `a` and `c`.” |

To count as a Σ-protocol, the protocol is designed to satisfy:

- **Completeness:** honest prover + honest verifier accept.
- **Special HVZK:** there is a simulator that can output an accepting
  transcript `(a, c, s)` without the witness, for any challenge `c`.
- **Special soundness:** given two accepting transcripts with the same
  commitment `a` but different challenges `c1 != c2`, you can efficiently
  extract the witness.

### A concrete instance: Schnorr for discrete log

Public parameters: a prime `p`, a subgroup of order `q`, and a generator `g`.

Statement: `y = g^x mod p` (public).

Witness: `x` (secret).

Protocol:

- Prover samples `r <- Z_q`, sends `a = g^r mod p`.
- Verifier samples `c <- Z_q`, sends `c`.
- Prover sends `s = r + c*x (mod q)`.
- Verifier checks `g^s == a * y^c (mod p)`.

From here:
- **HVZK simulator:** choose `c, s` first, then back-compute `a`.
- **Extractor:** two accepting responses to different challenges let you solve
  for `x`.

## Build It

### Step 1: The Σ transcript type
```python
@dataclass(frozen=True)
class SigmaTranscript:
    """A Σ-protocol transcript: (commitment, challenge, response)."""

    commitment: int
    challenge: int
    response: int
```
A Σ-protocol always produces a transcript with exactly these three fields. The
rest of the lesson is “just” designing how to generate and verify those fields.

### Step 2: Schnorr core operations
```python
@dataclass(frozen=True)
class SchnorrParams:
    """Toy subgroup parameters for Schnorr-style proofs.

    We work in the subgroup of Z_p* generated by g with prime order q.
    """

    p: int
    q: int
    g: int


def schnorr_public_key(params: SchnorrParams, x: int) -> int:
    x = x % params.q
    return mod_pow(params.g, x, params.p)


def schnorr_commit(params: SchnorrParams, r: int) -> int:
    r = r % params.q
    return mod_pow(params.g, r, params.p)


def schnorr_response(q: int, r: int, c: int, x: int) -> int:
    return (r + c * x) % q
```
These helpers are the “shape” of Schnorr: commitment is an exponentiation, and
the response is a linear relation in the exponent.

### Step 3: Prove and verify (completeness)
```python
def schnorr_prove(
    params: SchnorrParams, x: int, r: int, c: int
) -> SigmaTranscript:
    a = schnorr_commit(params, r)
    s = schnorr_response(params.q, r, c, x)
    return SigmaTranscript(commitment=a, challenge=c % params.q, response=s)


def schnorr_verify(params: SchnorrParams, y: int, a: int, c: int, s: int) -> bool:
    if not (0 <= c < params.q):
        return False
    if not (0 <= s < params.q):
        return False
    if not (0 <= a < params.p):
        return False
    left = mod_pow(params.g, s, params.p)
    right = mod_mul(a, mod_pow(y, c, params.p), params.p)
    return left == right
```
If the prover computes `a = g^r` and `s = r + c*x (mod q)`, the verification
equation holds by algebra: `g^{r+cx} = g^r * (g^x)^c`.

### Step 4: Special HVZK simulator (no witness)
```python
def schnorr_simulate_hvz(
    params: SchnorrParams, y: int, c: int, s: int
) -> SigmaTranscript:
    """Special HVZK simulator for Schnorr transcripts.

    Pick (c, s) and compute a so that verification passes:
      g^s = a * y^c   =>   a = g^s * (y^c)^(-1)  (mod p)
    """
    c = c % params.q
    s = s % params.q
    y_to_c = mod_pow(y, c, params.p)
    a = mod_mul(mod_pow(params.g, s, params.p), mod_inv(y_to_c, params.p), params.p)
    return SigmaTranscript(commitment=a, challenge=c, response=s)
```
The simulator reverses the order: it chooses the challenge and response first,
then computes a commitment that makes the transcript accept. If simulated and
real transcripts have the same distribution, the transcript cannot leak `x`.

### Step 5: Special soundness extractor (two transcripts -> witness)
```python
def schnorr_extract_witness(q: int, c1: int, s1: int, c2: int, s2: int) -> int:
    """Extract x from two accepting transcripts with same commitment and c1 != c2."""
    if c1 == c2:
        raise ValueError("need two different challenges to extract")
    num = (s1 - s2) % q
    den = (c1 - c2) % q
    return (num * mod_inv(den, q)) % q
```
If a prover can answer two different challenges for the same commitment, they
implicitly reveal the witness. This is why reusing randomness in Σ-protocols
is catastrophic.

## Use It

Sigma protocols show up everywhere:

- **Schnorr identification and Schnorr signatures:** the identification protocol is a Σ-protocol; Fiat–Shamir turns it into signatures.
- **Pedersen commitments:** proving knowledge of an opening (or equality of openings) is typically done with Σ-protocols.
- **zkSNARKs and larger ZK systems:** many constructions use Σ-protocols (or their generalizations) as sub-protocols, then combine them with Fiat–Shamir.

Rule of thumb: if you can write a verification equation of the form
“response-commitment relation holds”, you are probably looking at a Σ-protocol.

## Pitfalls

1. **Reusing the nonce `r`:** two transcripts with the same commitment let anyone extract the witness.
2. **Not validating subgroup membership:** if `y` is not in the intended subgroup, verification can become meaningless or exploitable.
3. **Tiny challenge space:** soundness error is about `1/|C|`; if `|C|` is small, cheating probability is large.
4. **Transcript not bound to the statement:** if `y` (and context) aren’t bound into the challenge (Fiat–Shamir), proofs can be replayed or transplanted.
5. **Mismatched moduli:** mixing `mod p` and `mod q` in exponent arithmetic silently breaks correctness and/or security arguments.

## Key Terms

| Term | What people say | What it actually means |
|------|------------------|------------------------|
| Σ-protocol | “3-round ZK proof” | A 3-move public-coin proof of knowledge with special soundness and (special) HVZK. |
| Transcript | “the proof” | The concrete `(a, c, s)` values the verifier checks. |
| Special HVZK | “simulatable” | There exists a simulator that outputs accepting transcripts without the witness, for chosen challenges. |
| Special soundness | “extractable” | Two accepting transcripts with the same `a` and different `c` reveal the witness. |
| Witness | “the secret” | The private value that makes the public statement true (e.g., `x` for `y=g^x`). |
