# LMS/HSS Integration Checklist (RFC 8554)

Use this as a PR-review checklist any time you see “add LMS/HSS signing” (firmware, package signing, artifact attestations, boot chains).

## Decision Guide

- Are you signing **many** objects with one key?
  - If yes, you need a Merkle-based construction (LMS/HSS or XMSS) rather than a pure OTS.
- Can you tolerate **statefulness** on the signer?
  - If no, prefer a stateless hash-based signature scheme (e.g., SPHINCS+) or a different PQ signature family.
- Is verification needed in a **very constrained** environment?
  - LMS verification is simple (hashing + parsing) but signatures are relatively large.

## Parameter & Format Checklist

- Fix and document the exact parameter sets you support (LMS typecode, LMOTS typecode).
- Reject unknown or deprecated typecodes at parse time.
- Enforce exact lengths:
  - `pubkey_len == 8 + 16 + m`
  - `sig_len == 4 + (4 + n + p*n) + 4 + h*m` for an LMS signature
- Define a canonical encoding for stored keys and signatures (binary + hex/base64 wrappers as needed).

## Signing-Side State Checklist (Highest Risk)

- Enforce **one-time key usage**:
  - Each signature must consume a unique leaf index `q`.
  - Never sign two messages with the same `(I, q)` / LM-OTS private key.
- Ensure **atomic `q` updates**:
  - Persist `q` *before* releasing the signature, or use a transactional write that commits `(q, signature)` together.
  - After crash/restart, `q` must never move backwards.
- Handle **concurrency**:
  - Use a single-writer lock or allocate non-overlapping `q` ranges per worker.
  - Avoid “read q → sign → write q+1” without a lock/transaction.
- Handle **exhaustion**:
  - When `q == 2^h`, fail closed and rotate keys.
  - Alert before exhaustion (e.g., at 80%, 90%, 95%).
- Backups & rollbacks:
  - Restoring an old snapshot of the signer database can roll `q` back and trigger reuse.
  - Treat signer state as append-only or monotonic.

## Randomness Checklist

- LM-OTS signatures include a per-signature randomizer `C`.
- In production, `C` must be generated by a cryptographically secure RNG.
- Never replace randomness with a deterministic function unless you fully understand the security implications (deterministic `C` is fine only for test vectors and educational demos).

## Verification-Side Checklist

- Parse defensively:
  - Check minimum lengths before slicing.
  - Reject mismatched typecodes (`sigtype`, `otssigtype`) early.
  - Reject `q >= 2^h`.
- Recompute:
  - LM-OTS public key candidate from `(I, q, message, lmots_signature)`.
  - Leaf hash from candidate.
  - Root hash by walking the authentication path.
  - Accept only if computed root equals public root.

## “Red Flag” Review Questions

- Where is `q` stored, and what prevents two signers from using the same `q`?
- What happens if the signing process crashes between generating a signature and updating `q`?
- Can a rollback (DB restore, VM snapshot restore, container redeploy) cause `q` reuse?
- Are all typecodes and lengths validated before any hash computations?
- Are signatures/public keys logged or displayed in a way that can be confused between hex/base64/binary?

## Operational Notes

- LMS/HSS is best treated as an **appliance**: a signing service with carefully managed state and backups.
- Consider a “signing allocation API” that reserves `q` values before signing (helps with concurrency and crash recovery).
- Build monitoring around:
  - `q` progress
  - exhaustion ETA
  - verification failures (to detect parsing/format mismatches)
