# FN-DSA (Falcon) Integration Review Checklist

Use this when reviewing a PR that adds or changes Falcon/FN-DSA signing, verification, or key handling.

## 0) Decide what you are standardizing on

- Exact parameter set(s) and algorithm identifiers (e.g., “512 vs 1024” variants).
- Exact signature format and transport (raw bytes, COSE/JOSE, X.509, custom).
- Whether you allow multiple implementations (and therefore need strict cross-compat test vectors).

If any of these are “TBD”, pause the integration: you will create accidental forks.

## 1) Inputs and encoding sanity checks

- Public key encoding: length is validated before decode; decode rejects out-of-range coefficients.
- Signature encoding: length is validated before decode; decode rejects invalid encodings (not “best effort”).
- Salt/nonce handling:
  - signature includes a salt/nonce (or your scheme documents why not),
  - verification uses the **same** bytes that signing used when computing `c = HashToPoint(salt || message)`.
- Endianness and canonical encoding are specified and tested.

## 2) Verification invariants (must be explicit)

Verification should be “one equation + one norm bound”:

- Recompute `c = HashToPoint(salt || message)`.
- Decode `s2` from the signature.
- Compute `s1 = c - s2*h (mod q)` in the correct ring.
- Center-lift `s1` into the intended integer range before computing the norm.
- Reject unless `||(s1, s2)||^2 <= beta^2`.

Red flags:

- Any verification code that “checks the equation” without the norm bound.
- Computing the norm on modulo-`q` coefficients without center-lifting.
- Confusing cyclic vs negacyclic ring multiplication (the `x^n = -1` wraparound sign matters).

## 3) Key provenance and lifecycle

- Keys are generated by a well-reviewed implementation; do not roll your own keygen.
- Private keys are stored with a clear format/version and are rotated under a documented policy.
- Public keys are authenticated (certificate, pinned key, transparency log, or an equivalent trust anchor).
- No accidental “key recovery” or “public key derivation from signature” mode unless explicitly intended.

## 4) Constant-time and side-channel posture

- Signing and key generation must be treated as side-channel sensitive.
- Make an explicit decision for your threat model:
  - “Remote attacker only” is different from “co-resident / local attacker”.
- Don’t log:
  - salts/nonces,
  - intermediate polynomial values,
  - “retry counts” or timing that correlates with secret-dependent sampling.

## 5) Test plan (non-negotiable)

- Roundtrip tests: sign then verify for a representative set of messages and keys.
- Negative tests:
  - flip one bit of the message → verify must fail,
  - flip one bit of the signature → must fail,
  - swap public keys → must fail,
  - truncated signature/public key → must fail.
- Cross-implementation tests (if you support multiple libraries):
  - sign with impl A, verify with impl B (and vice versa).
- Vector tests pinned in-repo:
  - at least one known-good keypair + multiple message/signature pairs.

## 6) Performance and operational checks

- Verify throughput meets target (Falcon is often chosen because verification is fast).
- Signature sizes are measured in the actual transport encoding (not just raw bytes).
- Memory/stack usage is reviewed for your deployment target (mobile, embedded, smart contract precompile, server).

## 7) Migration and agility

- Plan for algorithm agility:
  - allow adding/removing PQ signature algorithms without redesigning the wire format,
  - decide whether you need hybrids (classical + PQ) and how you bind them to the same identity.
- Document the “stop ship” conditions (e.g., upstream parameter change, critical implementation CVE).
