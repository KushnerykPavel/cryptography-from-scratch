# snarkjs Groth16 Artifact Audit Checklist

Use this when reviewing a PR or release that ships Groth16 artifacts produced with Circom + snarkjs.

## 0) You need these inputs (non-negotiable)

- The exact `verification_key.json` used by verifiers (backend / contract / mobile).
- The exact `public.json` and `proof.json` produced for at least one known-good input.
- The exact circuit build artifacts and versions:
  - `.circom` sources (and `circom` version)
  - `.r1cs` + `.wasm` (or a reproducible build that regenerates them)
  - the final `.zkey` (and snarkjs version)
- Trusted setup provenance:
  - which `.ptau` was used,
  - ceremony transcript/attestation, if applicable.

If you cannot name these precisely, you cannot audit correctness.

## 1) Sanity checks for `verification_key.json`

- `protocol` is `groth16`.
- `curve` matches the runtime verifier’s curve:
  - BN254 is commonly labeled `bn128` in snarkjs contexts.
- `nPublic` equals the number of public signals your application expects.
- `IC` length equals `nPublic + 1` (constant “1” term).
- Public input ordering is explicitly documented:
  - in the circuit comments/docs,
  - in the prover code,
  - in the verifier code.

## 2) Sanity checks for `public.json`

- It is a JSON array of decimal strings.
- Its length equals `nPublic`.
- Each value is < the curve’s scalar field modulus (enforce bounds in verifier code).
- Encoding into field elements is specified and consistent:
  - byte order,
  - fixed width,
  - hashing-to-field / packing scheme,
  - domain separation tags.

## 3) Sanity checks for `proof.json`

- It contains `protocol`, `curve`, and the three proof points:
  - `pi_a`, `pi_b`, `pi_c`.
- Point coordinate format is consistent with the verifier implementation:
  - some libraries use affine `[x, y]`,
  - snarkjs JSON often includes a projective/extended third coordinate (commonly `1`).
- Never accept “proof points” coming from an untrusted client unless:
  - verification runs server-side or on-chain, and
  - you bind the proof to a domain-separated statement.

## 4) Cross-file consistency checks

- `verification_key.json.curve` matches `proof.json.curve`.
- `len(public.json) == verification_key.nPublic`.
- `len(verification_key.IC) == len(public.json) + 1`.

These checks catch a huge class of “wrong key / wrong circuit / wrong input order” failures early.

## 5) Provenance checks (supply chain)

- Treat `.zkey` and `verification_key.json` as **release artifacts**:
  - store them immutably (content-addressed or checksummed),
  - pin tool versions in CI.
- Record SHA-256 hashes for:
  - `verification_key.json`,
  - `proof.json` (for test fixtures),
  - `public.json`,
  - `.r1cs`, `.wasm`, `.zkey`.
- Don’t “regenerate keys on deploy” without pinning everything; you’ll ship silent mismatches.

## 6) Negative tests you must have

- Mutate one public signal → verification must fail.
- Swap public signal order → must fail.
- Mutate `pi_a`/`pi_b`/`pi_c` → must fail.
- Verify the same proof with the wrong `verification_key.json` → must fail.

## 7) Common mistakes to grep for

- Off-by-one in `IC` indexing (`IC[i]` vs `IC[i+1]`).
- Public signals treated as integers without field bound checks.
- Mismatched `bn128`/BN254 naming across toolchains.
- Mixing artifacts generated by different snarkjs versions.
- Accidentally changing the circuit while reusing an old `.zkey`/verification key.

## 8) Red flags (escalate immediately)

- No clear provenance for the `.ptau` / setup ceremony.
- Keys/proofs stored in a mutable location (e.g., S3 bucket overwritten in-place) without checksums.
- “It verified once locally” without automated negative tests.
- Any ambiguity about public input ordering.
